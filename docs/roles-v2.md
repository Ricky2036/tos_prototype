## 一、Codex 的两种存在形式

Codex 有两个入口，**角色相同、投递方式不同**：

| 形式 | 是什么 | 能不能被我直接发消息 |
|---|---|---|
| **ChatGPT.app**（客户端） | 就是 Codex 的桌面客户端，可对话、可读仓库 | **要开 `--remote-debugging-port` 才能**（默认没开，只有私有 unix socket，不去碰） |
| **codex CLI** | `codex exec` / `agent-autoloop` 调用 | 可以，但必须有明确的输入输出契约 |

只被**调用**的那种形式，决定三件事：

1. **产出必须是文件**，不能是一段对话 —— 否则这轮结束就没了。
2. **调用要批量**。一次调一张单是浪费：今天实测 4 轮试跑烧了 32 万 Token，
   调试早报又烧掉 ~70 万。
3. **它不该做重复劳动**。跑构建、跑 e2e、跑全量单测，机器做比它做便宜一万倍。

> 客户端开着时，前两条可以放松：对话能迭代，不必一次吃三张单。
> 但**额度纪律不变**——那是账户属性，不是通道属性。

## 二、角色表（v2）

| 角色 | 谁 | 干什么 | 额度 | 触发方式 |
|---|---|---|---|---|
| **规划者** | **Codex**（ChatGPT 客户端 / CLI） | 任务拆解、排优先级、架构决策、审查、难缺陷定位 | **紧，计量使用** | 按需：客户端直连，或 `run 拆解` 批量调用 |
| **集成者** | Antigravity | 独占主干合并、发布流水线、跑门禁、共享面治理、冲突仲裁 | 充足 | 常驻 |
| **构建者** | Workbuddy | 按单实现、自验 | 充足 | 拉取队列 |
| **基建** | DSH | 门禁、工具、唯一真机采集与保活、断言溯源 | 充足 | 常驻 |
| **决定** | 用户 | 真实权限阻塞或产品重大取舍拍板 | — | 卡片 / 对话 |

**`tos-codex` worktree 不启用。** Codex 负责规划、排优先级与审查，实现优先分配给 WB / AG / DSH 三人，不写业务实现代码；所有分支成果经 Antigravity 统一集成验证后合入 `main`，任何角色均不直接向 `main` 提交未经验证的变更。

投递方式按可用性选：**客户端能直连就直连**（一条消息即到），否则用
`agent-autoloop run 拆解` 或 `codex exec --cd <repo>`。

## 三、成本路由表（最重要的一张表）

接到一件事，先按这张表分流，**别默认扔给 Codex**：

| 活的类型 | 给谁 | 判据 |
|---|---|---|
| 「这件事该怎么拆」「方案 A 还是 B」「为什么反复红」 | **Codex** | 需要一次性想清楚、且想错的代价高 |
| 「按这张单改这几个文件」 | WB / AG | 有明确验收命令，机械执行 |
| 「给某条规则加个门禁」「修工具」「真机采集」 | DSH | 基建与真机所有权 |
| 「合入 / 拆冲突 / 发布流水线」 | AG | 集成者 |
| 「先做哪个」 | Codex | Codex 主导排优先级与直接派单，用户已全面授权 |

**三条硬规矩：**

1. **Codex 一次至少处理 3 张单。** 一张一调是烧钱。
2. **Codex 的输入必须先压成一页**：现状、约束、期望产出文件路径。不让它自己翻仓库。
3. **Codex 不跑** `npm run build` / `run-e2e` / 全量单测 —— 这些交给门禁脚本。

## 四、队列与认领（取代「派单给谁」）

```
.tasks/queue/Q-001.md
```

```yaml
id: Q-001
size: S              # S ≤2h / M ≤半天 / L ≤1天，L 必须先拆
status: ready        # ready | doing | blocked | done
claim: C2            # 归属是「簇」，不是「人」
owner: —             # 取单时填自己，做完置 done
depends: []
```

规则：

- **谁能干谁干。** 谁空闲就取 `ready` 且未被占用的单，取的时候填 `owner` 并登记 `.claims/`。
- **做完不是做完**：必须贴门禁结果（`node scripts/gate-merge.mjs`）。
- 同一张单只能有一个 owner；两个人想抢，先到先得，后者取下一张。

## 五、Codex 的调用契约

### 什么时候调

- 队列里出现 **≥3 张 `size: L`** 或互相纠缠的单
- 同一个红色反复出现 ≥2 次（说明不是手滑，是设计问题）
- 要改架构（注册点、门禁口径、目录结构）

### 怎么调

```bash
# 方式一：直接调（我或 AG 手动）
codex exec --cd <repo> --sandbox read-only -m gpt-6.1-sol "<压缩后的一页上下文>"

# 方式二：走 agent-autoloop（有记录、可续、可发卡片）
agent-autoloop run 拆解
```

### 输出契约（不给这个它会写散文）

必须产出：

1. `.tasks/queue/Q-*.md` —— 拆好的单，每张都有 `size` / `claim` / `depends` / 验收命令
2. `docs/decisions.md` —— 追加一条：决策、理由、被否掉的方案
3. 回复最后 6 行以内摘要：拆成了几张、依赖关系、建议的开工顺序

**不接受**：只给建议不落单、不写验收命令、把「调研一下」当产出。

## 六、额度纪律

| 做法 | 为什么 |
|---|---|
| 批量调用 | 今天实测：4 轮 32 万 Token，其中 84% 是缓存命中；单轮成本主要来自重复读仓库 |
| 先压上下文再调 | 让 Codex 自己 grep 仓库，等于让它把额度花在搬运上 |
| 不让它跑构建/测试 | 一次 `run-e2e --all` 632 秒，机器做不要钱 |
| 拆完立刻停 | 拆解完成后不要顺手让它实现——那是 WB/AG 的活 |

**额度预警**：`agent-autoloop status` 每天会显示 Token 消耗。
