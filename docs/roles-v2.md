## 一、为什么 Codex 的角色不一样

Codex 是 **CLI，没有 GUI 窗口**。它不能像 AG / WB 那样常驻对话、被我叫去干活；
它只能被**调用**：给一段提示词、一个目录，跑一轮，输出，退出。

这决定三件事：

1. **它的产出必须是文件**，不能是一段对话。否则这轮结束就没了。
2. **它的调用要批量**。一次调一张单是浪费——今天的实测：4 轮试跑烧了 32 万 Token，
   调试早报又烧掉 ~70 万。
3. **它不该做重复劳动**。跑构建、跑 e2e、跑全量单测这类活，机器做比它做便宜一万倍。

## 三、成本路由表（最重要的一张表）

接到一件事，先按这张表分流，**别默认扔给 Codex**：

| 活的类型 | 给谁 | 判据 |
|---|---|---|
| 「这件事该怎么拆」「方案 A 还是 B」「为什么反复红」 | **Codex** | 需要一次性想清楚、且想错的代价高 |
| 「按这张单改这几个文件」 | WB / AG | 有明确验收命令，机械执行 |
| 「给某条规则加个门禁」「修工具」 | DSH | 基建所有权 |
| 「合入 / 拆冲突」 | AG | 集成者 |
| 「先做哪个」 | 你 | 只有你能定 |

**三条硬规矩：**

1. **Codex 一次至少处理 3 张单。** 一张一调是烧钱。
2. **Codex 的输入必须先压成一页**：现状、约束、期望产出文件路径。不让它自己翻仓库。
3. **Codex 不跑** `npm run build` / `run-e2e` / 全量单测 —— 这些交给门禁脚本。

## 四、队列与认领（取代「派单给谁」）

```
.tasks/queue/Q-001.md
```

```yaml
id: Q-001
size: S              # S ≤2h / M ≤半天 / L ≤1天，L 必须先拆
status: ready        # ready | doing | blocked | done
claim: C2            # 归属是「簇」，不是「人」
owner: —             # 取单时填自己，做完置 done
depends: []
```

规则：

- **谁能干谁干。** 谁空闲就取 `ready` 且未被占用的单，取的时候填 `owner` 并登记 `.claims/`。
- **做完不是做完**：必须贴门禁结果（`node scripts/gate-merge.mjs`）。
- 同一张单只能有一个 owner；两个人想抢，先到先得，后者取下一张。

## 五、Codex 的调用契约

### 什么时候调

- 队列里出现 **≥3 张 `size: L`** 或互相纠缠的单
- 同一个红色反复出现 ≥2 次（说明不是手滑，是设计问题）
- 要改架构（注册点、门禁口径、目录结构）

### 怎么调

```bash
# 方式一：直接调（我或 AG 手动）
codex exec --cd <repo> --sandbox read-only -m gpt-6.1-sol "<压缩后的一页上下文>"

# 方式二：走 agent-autoloop（有记录、可续、可发卡片）
agent-autoloop run 拆解
```

### 输出契约（不给这个它会写散文）

必须产出：

1. `.tasks/queue/Q-*.md` —— 拆好的单，每张都有 `size` / `claim` / `depends` / 验收命令
2. `docs/decisions.md` —— 追加一条：决策、理由、被否掉的方案
3. 回复最后 6 行以内摘要：拆成了几张、依赖关系、建议的开工顺序

**不接受**：只给建议不落单、不写验收命令、把「调研一下」当产出。

## 六、额度纪律

| 做法 | 为什么 |
|---|---|
| 批量调用 | 今天实测：4 轮 32 万 Token，其中 84% 是缓存命中；单轮成本主要来自重复读仓库 |
| 先压上下文再调 | 让 Codex 自己 grep 仓库，等于让它把额度花在搬运上 |
| 不让它跑构建/测试 | 一次 `run-e2e --all` 632 秒，机器做不要钱 |
| 拆完立刻停 | 拆解完成后不要顺手让它实现——那是 WB/AG 的活 |

**额度预警**：`agent-autoloop status` 每天会显示 Token 消耗。

| 情况 | 谁处理 |
