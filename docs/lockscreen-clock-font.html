③ 反解过程：从参考图到字体参数

可变字体的 fvar 里有两个轴。轴名不可信，必须实测——两个轴的真实语义如下（用 fontTools 对 glyf 轮廓实测）：

轴量程实测语义默认值
wght100–1000只改笔画粗细，对字形高度零影响（实测 h_em 恒为 0.470）100
ytde0–1000顶部锚定的垂直缩放：yMax 恒定 2840、yMin 从 +884 一路下探到 −7500，advance 不变。高度 0.470em → 2.565em（×5.46）0

注意两个默认值都是最小值——不显式给轴，字体就是「极细且极扁」的样子。

解算：三个目标 → 三个参数

「宽高比」和「笔画占宽比」都是无量纲量，先把它们解出来，就绕开了缩放的不确定性：

# 整串「17:56」实测：K_em = 1.6322（ink 宽 / em），top_em = 0.7100（基线到 ink 顶，恒定）
# ytde 对高度的影响是完美线性的：h_em = 1.3278 + (ytde − 400) × 0.0021055

目标宽高比  = 280.7 / 273.3          = 1.0271
  ⇒ 1.6322 / h_em = 1.0271            ⇒ h_em = 1.5892   ⇒ ytde = 525

目标笔画占宽 = 20.5 / 280.7           = 0.07303
  ⇒ stroke_em = 0.07303 × 1.6322      = 0.11920         ⇒ wght = 841

目标视觉高   = 273.3
  ⇒ font-size × 1.5892 = 273.3        ⇒ font-size = 172

# 自洽校验（等比缩放下 scale = 1）
172 × 1.6322 = 280.7  ✓ 命中视觉宽
172 × 0.1192 = 20.5   ✓ 命中笔画宽

关键设计：用 ytde 轴拉伸，而不是用 viewBox 非等比拉伸

原实现靠 viewBox="0 0 280 84" + preserveAspectRatio="none" 把 SVG 盒（306×220）非等比拉扁，纵向多拉伸 2.397 倍。这个做法的问题是：笔画、字距、圆角全都被一起压扁了，字形的设计意图被破坏。

新做法是让 viewBox 与 SVG 盒 1:1（306×305，scale = 1，等比），高度完全交给 ytde 轴——该轴的设计意图正是「顶部锚定、把字拉长」，笔画粗细和字宽完全不受影响。参考图的宽高比是 1.027，字体原生的宽高比是 3.30，这 3.21 倍的差距恰好由 ytde 的 ×5.46 量程覆盖。

技术验证：浏览器对自定义轴的驱动能力已被证实——若 ytde 未生效（=0），数字高度只会是 172 × 0.490 = 84 px；实测 273.7 px，说明 font-variation-settings: "wght" 840, "ytde" 525 两个轴都被正确应用。

font-variation-settings 优先于 font-weight；若字体回退到系统字体，该声明被忽略、仍走 font-weight 降级链——这是天然的安全网。

⑤ 必须知道的布局联动

CLOCK_MAX_HEIGHT 从 220 提到 305 是「数字变高」的必然结果——容器高度同时决定了通知卡片的起始位置和上滑挤压的行程：

派生量改前改后含义
clipTop313398通知／活动卡片队列的起始 y，下移 85
HIT_DISTANCE251170上滑多少像素后开始挤压时钟
EXPAND_SCROLL_Y110195挤压总行程（max → min）

取舍点：保持 220 不动可以让挤压节奏完全不变，但数字底边（378）会压到通知卡片区（313 起）65 px。当前选择提高到 305，让容器真实容纳内容、数字不与卡片重叠——代价是上滑挤压的行程变长。

若希望保留原节奏，把 CLOCK_MAX_HEIGHT 改回 220 即可（数字仍会完整渲染，因为 .ls-inner 与 svg 都是 overflow: visible，只是会叠在卡片上）。

⑥ 挤压态的三个问题与根因

展开态达标之后，上滑挤压到最小态暴露了三处问题（参考图 2 即真机最小态）。三者其实是同一个根因的三个侧面：

现象根因证据
数字变形（被纵向压扁、笔画变细长） .ls-clock svg { height:100% } 让 SVG 盒跟着容器从 305 缩到 110。而 viewBox 是固定的 306×305 ⇒ scaleY 掉到 0.36 而 scaleX 恒为 1 ⇒ 非等比压扁 scaleY 0.36 / scaleX 1.00
和日期挤在一起 同一根因的副作用：字形被等比缩小后顶边往下带到 y ≈ 87，压在日期的视觉底边（88.35）上 ink 顶 87 < 88.35
顶部起始位置漂移 y 是写死的常量 149.8（按展开态 font-size 172 算出来的）。字号一变小，「基线 → ink 顶」的绝对距离也跟着变小，再加上 scaleY 收缩，顶端位置完全失控 y 恒定 ⇒ 顶边下移 17.7 px

一句话：旧实现把「挤压」做成了「把整张画布按纵向压扁」，而不是「把字变小」。前者必然同时改变笔画比例和顶边位置——两个症状一起出现，不可能只修一个。

⑦ 新策略：SVG 盒固定，缩放交给 font-size + ytde

两条硬约束：

  • SVG 的 CSS 盒高恒为 305px（= viewBox 高）⇒ scale 恒为 1 ⇒ 从结构上排除非等比压扁的可能；
  • 高度变化全部由 font-size 与 ytde 轴插值承担。

顶部固定的数学基础

字体实测 top_em = 0.7100（基线 → ink 顶，以 em 计），并且在 ytde 0 → 525 的全量程内恒定——这正是「ytde 是顶部锚定缩放」的直接推论。于是只要令

y = CLOCK_INK_TOP_OFFSET + font-size × 0.7100
  = 27.7 + font-size × 0.7100

# 校验
展开态  y = 27.7 + 172 × 0.7100 = 149.82  ⇒ ink 顶 = 77 + 27.7 = 104.7
最小态  y = 27.7 + 151 × 0.7100 = 134.91  ⇒ ink 顶 = 77 + 27.7 = 104.7

容器顶在 CLOCK_TOP = 77，CLOCK_INK_TOP_OFFSET = 27.7 是「ink 顶相对容器顶」的偏移。y 随字号一起变小 ⇒ 两者恰好抵消 ⇒ 顶端绝对位置恒定。

三层结构

层内容作用
① clipPath与霜面逐字同款的 <text>（x / y / font-size / 轴 / text-anchor / letter-spacing 全部一致）字形轮廓
② 玻璃本体壁纸自身 + feGaussianBlur，被①裁切真·背景模糊（= backdrop-filter 的等价物）
③ 霜面半透明白渐变填充（objectBoundingBox，随字形高度铺满）受光感 + 让壁纸透出来
 
// 壁纸 rect 就是「屏幕 rect」映射到 svg user space（见下）
<g clip-path="url(#ls-clock-glyph)">
  <image href={wallpaper} x="-27" y="-77" width="360" height="788"
         preserveAspectRatio="xMidYMid slice" filter="url(#ls-clock-blur)" />
</g>
<text fill="url(#ls-clock-frost)">18:46</text>

为什么不用 backdrop-filter：Chromium 不支持 SVG 元素上的 backdrop-filter；而 HTML 元素上即使支持，它也只模糊元素的矩形盒，没法裁成字形——CSS mask-image 只能指向外部图片，data-URI SVG 里又加载不到页面字体。

所以走「壁纸自身 → 模糊 → 被字形裁切」这条路：半径完全可控、不依赖浏览器怪癖，而且和真实折射玻璃的物理一致。

取样窗必须钉在屏幕上（唯一容易做错的地方）

玻璃要「贴住壁纸」，所以取样窗必须落在屏幕坐标系里，而不是跟着数字跑。svg 的 user unit 与 CSS px 1:1（viewBox 306×305 ↔ 盒 306×305），于是静止态壁纸在 svg 坐标里就是：

x = −27  y = −77  w = 360  h = 788
// svg 顶在 CLOCK_TOP = 77、`.ls-clock` 是 flex 居中 ⇒ 左偏 (360 − 306)/2 = 27

但上滑解锁时 .ls-inner 会 translateY(−p·240) scale(1 − p·0.04)（原点在屏心），壁纸却不动。所以必须对同一变换做逆映射，否则解锁过程中字形里的壁纸图案会跟着数字整体平移，很假。

s  = 1 − p·0.04        ty = −p·240
x = (W/2 + (0 − W/2)/s − svgLeft) / kx
y = (H/2 + (0 − H/2 − ty)/s) − CLOCK_TOP
w = (W/s) / kx         h = H / s        // kx = 85%·W/306，纵向恒为 1

校验方式：用 getScreenCTM() 量 <image> 真正落在屏幕上的矩形。p = 0 / 0.25 / 0.5 / 0.75 / 1 五点全部精确等于屏幕矩形 (0, 0, 360, 788)，误差 0.00 px。

⑩ 量测中踩到的坑

  • 轴名会骗人：ytde 的注册名是「Descender Depth」，听起来只管降部；实测是顶部锚定的整体垂直缩放（yMax 恒定、yMin 下探）。判断轴语义只能靠插值后量 glyf 轮廓。
  • 默认实例是最小值：wght 默认 100、ytde 默认 0。不显式给轴，字体渲染出来是「极细且极扁」的，与目标相差一个数量级。
  • getBBox() 量不到字形高度：对 SVG <text> 返回的是字体度量盒（≈95 用户单位，恒定），对轴变化完全无感。必须像素量测。
  • 用 Pillow 建立解析模型，比在浏览器里扫网格快一个数量级：Pillow 支持 set_variation_by_axes()，可以在 Python 侧直接得到「高度/笔画宽/整串宽 vs 轴值」的解析表，反解出参数后只在浏览器验证一轮。
  • 参考图量测要点：数字是半透明白叠在彩色壁纸上，差分法会被壁纸高光污染 ⇒ 改用「亮度阈值 + 低饱和度」定点扫描，并沿竖笔列做纵向连续段扫描定底边。
  • 同一参数在不同字符串下宽度不同：该字体是比例数字（hmtx 里 '1' 的 advance 是 0.341em、'5'/'6' 是 0.390em），且字体没有 GSUB，无法通过 font-variant-numeric: tabular-nums 切成等宽。所以「18:07」实测 285.7、「18:1x」287.3，随分钟变化有 ±4 px 的浮动——这是字体固有权重，不是参数没调准。
  • 参考图是手持照片：存在透视畸变，因此「宽度」类指标的绝对可信度低于「高度」和「位置」类指标。
  • 量测窗必须按「容器底」兜住，不能按 scrollTop 二分：挤压态的第一版量测脚本按「scrollTop < 250 用 1160 px、否则用 600 px」选窗口，结果 scrollTop = 180 那一点把上移中的通知卡片顶边（1152 px）算了进去， ink 底虚高到 386.3（≈ 卡片边）⇒ 误判成「高度不降反升」。改成「时钟容器底 + 8 px」作下界后，该点立刻回到模型值 258.3。
  • 判「有没有变形」要拿实测对比字体模型，不能只看高度变化：高度随挤压变小本身就是预期结果。真正的判据是「实测高 ÷ 字体模型高」是否恒为 1——模型只跟 font-size × h_em(ytde) 有关，与容器高、SVG 盒都无关，所以任何非等比压扁都会在这里暴露。
  • 「半透明白字」和「毛玻璃」不是一回事，而且能定量区分：只把 fill 改成 rgba(255,255,255,0.47)，笔画里的壁纸细节会原样透出，梯度能量比仍 ≈ 1。真玻璃必须让背景先被模糊再被字形裁切。反过来，判断别人（或自己）做的是哪一种，就用「笔画内 / 笔画外 梯度能量比」——参考图实测 0.376，σ=0 对照实测 0.602。
  • 用数值对齐之前必须先做「关掉效果」的对照：本轮的「笔画内/外比值」量法自带 0.602 的偏置地板，若直接拿参考图的 0.376 去对齐，会解出偏小的 σ。任何「把某个比值调到和参考图一样」的标定，都要先量一次「效果关闭」时该比值是多少。
  • Chromium 不支持 SVG 元素上的 backdrop-filter；HTML 元素上虽然支持，但它只作用于元素的矩形盒，无法裁成字形（CSS mask-image 只能指向外部图片，而 data-URI SVG 里加载不到页面 @font-face）。要「形状化的毛玻璃」只能自己合成：把背景图像模糊后用 clipPath 裁进字形。
  • 把背景图搬进 SVG 当纹理时，取样窗要对「祖先的 transform」做逆映射：否则动画一开始，字形里的纹理就会跟着字形整体平移。验收方式是用 getScreenCTM() 量 <image> 实际落在屏幕上的矩形，逐点比对目标屏幕矩形。

⑪ 未决 / 待确认

  • 玻璃的三个参数是可调的（见 ⑨）：CLOCK_GLASS_BLUR（模糊半径，现 6）、CLOCK_GLASS_ALPHA_TOP / _BOTTOM（霜面不透明度，现 0.495 / 0.46）。 σ 调大 ⇒ 更「磨砂／奶」；调小 ⇒ 更「清玻」；调到 0 ⇒ 退化成半透明白字（不是玻璃）。若你觉得数字「太淡」，把两个 alpha 一起往上加即可（不影响任何几何标定）。 ⚠️ 注意 `.ls-clock` 自己还有 opacity: .95，会再乘一次 —— 想让屏上有效 α 等于 0.47，霜面要写 0.495。
  • 玻璃取样的是原始壁纸，未叠 .ls-wallpaper::after 那层暗化（最多 18%）⇒ 字形比背板略亮。物理上这正是毛玻璃散射环境光的效果，故保留；若要完全贴合，可在 blur 后加一层等量的 feComponentTransfer。
  • 最小态宽度按字符串浮动：参考图最小态是「18:16」（242.7），实测最小态是「18:25」（251.0）。宽度端点是用同一串反解对齐的，所以这里 +3.4% 是字符组合差异，不是参数没调准——与展开态 ±4 px 的跳动同源（见 ⑩）。
  • 数字宽度随分钟跳动（±4 px，见 ⑨ 最后两条）。若要消除，需给字体补 tnum 特性表，或改用等宽数字字体——需要你决定是否值得。
  • 上滑挤压行程变长（110 → 195，见 ⑤）。若觉得手感变了，把 CLOCK_MAX_HEIGHT 调回 220 即可（但会压到卡片区）。
  • Safari 真机未验：本机 Playwright 的 WebKit 驱动版本不匹配（需要 webkit-2312，本机只有 webkit-2311），无法自动化验证。Chrome 已确认支持 ytde 轴驱动。
  • 字号 16px 的日期：参考图日期明显比原型原设计更小更精致，已按参考图改小（22 → 16）。若你觉得偏小可回退。
  • 最小态的视觉"分量"：参考图最小态笔画 ≈ 18、本实现 18.5，已对齐；若希望最小态更"轻"一些，把 CLOCK_WEIGHT 从 840 往下调即可（它不参与挤压插值，是全局常量）。
